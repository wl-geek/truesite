# TrueSite audit: 15 Oct 2026

## Scope and method

This is a read-only audit of `main` at `7de9258`, taken two days before submission. It covers the web app, the server, deploy, BIM data, the GenAI layer, tests and docs. Ten auditors each took one area:

- pose maths and frames
- WebXR AR modes
- browser check pipeline
- server core
- security
- phone UX and error paths
- deploy
- BIM data
- GenAI layer
- tests, docs and dead code

There was no extra gap round, because the run was scaled down to save tokens.

Review:

- Every high and medium finding had two independent reviewers: one tried to refute it, one tried to reproduce it. A third reviewer settled any disagreement.
- Every low finding had one reviewer who tried to refute it.
- Refuted findings are listed under "Considered and rejected".
- Where several areas reported the same root cause, the reports are merged into one finding. The merged finding keeps the highest severity the evidence supports.

Reproductions used throwaway scripts in the scratchpad and temporary vitest files under `web/src/__audit_tmp__/`, all deleted afterwards. The working tree was left clean.

**A-00 · Test suite isn't portable to Windows**

- Severity: Low · Area: Tests & docs · Status: **Fixed** in #40, which also makes the BIM JSON writers use LF on every OS
- Location: `server/tests/test_docs_links.py`, `server/tests/test_spa.py`, `bim/tests/test_models_room1.py`
- Evidence:
  - `test_docs_links.py` reads files in the locale encoding (cp1252).
  - `test_spa.py` writes CRLF through `write_text`.
  - IfcOpenShell triangulates differently on Windows, so the glb differs in its index buffers only. Vertices and JSON are identical.
- Fix: read as UTF-8, write with `newline="\n"`, and compare the glb by content (JSON, vertices, surface area) when the bytes differ.

#### A-01 · Default focal length uses the short side in portrait

**Status:** Fixed in #43

- **Severity:** High · **Area:** Pose
- **Location:** `web/src/camera/intrinsics.ts:51`; also `web/src/calib/collect.ts:25`, `web/src/camera/intrinsics.test.ts:25`, `docs/plans/2026-10-11-truesite-contract.md:253`
- **Evidence:**
  - The fallback is `focalFromHfov(DEFAULT_HFOV_DEG, videoW)`.
  - Portrait frames arrive already rotated (`camera.ts:10`; iOS gives videoWidth < videoHeight). A 1080×1920 frame therefore gets f = 881 px, but the same lens in landscape gets 1567 px.
  - The 63° default is a long-side value: the research notes' prior is 1044 px at 1280×720.
  - `intrinsics.test.ts:25` pins the short-side value. The `ViewCollector` prior has the same flaw.
- **Impact:** Every uncalibrated portrait session is affected: the iPhone overlay and the D1/L1/R2 sheets, whenever a user taps Skip or calibration fails.
  - The overlay is visibly off: 120–260 px median on L1/R1 in simulation.
  - The distance reads about 57% of the true value, and D1 grades "poor".
  - The check's design render uses the same wrong K, so Gemini compares misaligned images.
  - WebXR place-by-code is not affected, because it uses its own K.
- **Proposed fix:**
  - Use `focalFromHfov(DEFAULT_HFOV_DEG, Math.max(videoW, videoH))` in both `intrinsics.ts` and `collect.ts`.
  - Update the test and contract §7 to say "63° across the long side".
- **Test:**
  - Failing test first: `expect(loadIntrinsics(1080, 1920).f).toBeCloseTo(loadIntrinsics(1920, 1080).f)`. Today it gives 881 vs 1567.
  - Then a pose test: a synthetic portrait D1 view with true f ≈ 1507 should grade `good`, with the distance within 10%.
- **Verification:** Four reviewers ran independent simulations with the real `estimatePose` and `loadIntrinsics`. They confirmed that calibration still converges within 0.65% in portrait, so only skipped or failed calibration is affected.

#### A-02 · Place-by-code ring measures the angle around the IFC origin, not the code

**Status:** Fixed in #42 (regression test #46)

- **Severity:** High · **Area:** WebXR
- **Location:** `web/src/scene/xrPlace.ts:131`; also `web/src/scene/xrPlace.ts:194`, `web/src/scene/xrPlace.test.ts:38`
- **Evidence:**
  - The code is `viewSpreadDeg(fused.position, estimates.map((e) => e.cameraPos))`.
  - `fused.position` is the translation of `viewM × modelMatrixIfc(...)`, which is the world position of IFC (0, 0, 0), not the code.
  - R1/R2 sit at IFC (4.5, 4.5, 0), 6.36 m from that origin. L1 sits 2.5 m from it.
- **Impact:** With the coached ±0.6 m sweep, R1 measures 7.6° against 45.2° around the code. `NEEDED_SPREAD_DEG` is 25, so the ring stops at about 30%, `lock()` never runs and the model never appears. That is the Android hero demo.
  - L1 tops out at about 67%.
  - The "° of angle" readout is wrong as well.
- **Proposed fix:**
  - Store `codePos = new Vector3(...anchor.position_m).applyMatrix4(m)` on each estimate.
  - Measure the spread around the mean `codePos`.
  - Extract a pure `placementProgress(estimates)`.
- **Test:** Build exact R1 estimates with cameras at (±0.6, 1.2, 0.8) m around the code and assert a spread > 25° (about 45°). It fails today with 7.6°.
- **Verification:** Four reviewers reproduced it with the real `modelMatrixIfc`, `fuseEstimates` and `estimatePose`. An anchor placed at the IFC origin gives the same number both ways, which is why the existing unit test misses it.

#### A-03 · Start AR drops the 1:20 desk scale

**Status:** Fixed in #42

- **Severity:** High · **Area:** WebXR
- **Location:** `web/src/scene/xrPlace.ts:140`; also `web/src/scene/xrPlace.ts:197`, `web/src/ui/LivePage.tsx:397`, `web/src/ui/LivePage.tsx:245`
- **Evidence:**
  - `m.decompose(position, quaternion, new Vector3())` throws away `anchor.scale` (0.05).
  - `lock()` then composes with `new Vector3(1, 1, 1)`.
  - "Start AR (place by code)" is the primary button whenever `xrOk`, with no `!desk` guard. Walk inside does have that guard.
  - The camera-access fallback to `walkInside()` also ignores desk anchors.
- **Impact:** An Android judge with the D1 desk sheet gets a life-size 4 × 3 × 2.7 m room about 2.4 m from the sheet, instead of the 1:20 model beside it.
- **Proposed fix:**
  - Use `world.compose(fused.position, fused.quaternion, new Vector3().setScalar(o.anchor.scale))`, which reproduces `m` to 1e-17.
  - Never fall back to `walkInside()` for desk anchors. That change belongs with A-09.
- **Test:** Extract a pure `lockedMatrix(fused, scale)`. For D1, assert that `anchor.position_m` maps to the code's world point within 1 mm, and that a 4 m edge maps to 0.2 m. Today the error is 2.44 m and the edge is 4.0 m. Keep an L1 case unchanged.
- **Verification:** Four reviewers used temporary vitests with the real D1 anchor: the decomposed scale is 0.05 and the code lands 2.437 m off.

#### A-04 · Issues page lists only room1

**Status:** Fixed in #48

- **Severity:** High · **Area:** Web UI
- **Location:** `web/src/ui/IssuesPage.tsx:40`; also `web/src/api/client.ts:117`, `web/src/ui/ViewerPage.tsx:12`, `web/src/ui/LivePage.tsx:365`
- **Evidence:**
  - The page calls `listIssues(DEFAULT_PROJECT_ID)` with `DEFAULT_PROJECT_ID = 'room1'`.
  - The client always sends `?project_id=`, and the server filters on it (`server/app/routes/issues.py:63`).
